Technical Case Study / ArisAI Trading Platform

How We Built an AI-Powered Trading Platform

Two developers. Six months. A monorepo spanning web, mobile, real-time data, AI chat, live streaming, and payments. This is the technical story of building ArisAI from architecture decisions to production.

01

The Challenge

ArisAI needed to be a full ecosystem for retail traders, not just another charting tool. The requirements list was long: real-time trading dashboards with live WebSocket data, an AI chat assistant powered by Claude with streaming responses, signal rooms where providers broadcast live trade calls, a marketplace with Stripe subscriptions, live video streaming for podcasts, a mobile app with feature parity, multi-strategy authentication (Google, Apple, Instagram, Twitter, Telegram, and email, plus two-factor), gamification with tournaments and leaderboards, and a Stripe-powered subscription marketplace.

Each of these would be a significant feature in isolation. We needed all of them working together in a monorepo, with shared types between web and mobile, consistent real-time state, and a backend that could handle concurrent WebSocket connections across signal rooms, chat, and live trading data.

I joined the project about 3 months after my co-developer had started the NestJS backend. I was finishing my internship at Telecloud Vision in Beirut. Once I came onboard, I took ownership of roughly 80% of the frontend across all packages.

Architecture

The platform is a monorepo with four packages: a React 18 web app, a Next.js landing page, an Expo 52 mobile app, and a Remotion video generator. The backend is a NestJS API with PostgreSQL, Prisma ORM, Redis caching, and multiple real-time gateways.

Key Decisions

Every project has turning points where you pick one path over another. These were ours.

NestJS vs Express
NestJS won for structure
With 15+ pages worth of API endpoints, WebSocket gateways, guards, interceptors, and service layers, Express would have turned into spaghetti. NestJS gave us modules, dependency injection, and decorators that kept the backend organized as it scaled. The opinionated structure meant my co-developer and I could work on different modules without stepping on each other.
Zustand vs Redux
Zustand for speed and simplicity
We had real-time data flowing through WebSockets, AI chat state, auth state, and UI state all at once. Redux would have meant boilerplate for every slice. Zustand let us create focused stores with zero boilerplate. The devtools integration was good enough for debugging, and the bundle size difference mattered for our performance-sensitive trading views.
Amazon IVS vs alternatives
IVS for managed live streaming
We evaluated self-hosted solutions and other providers. Amazon IVS gave us low-latency live video with built-in chat, timed metadata for syncing UI events to the stream, and automatic transcoding. The trade-off was vendor lock-in, but for a two-person team, not having to manage streaming infrastructure was worth it.
Auth strategy
Passport with 6 strategies
Our users needed to sign in with Google, Apple, Instagram, Twitter, Telegram, and email/password, with two-factor on top. Passport gave us a consistent interface across all six. Each was a NestJS guard, and we composed them with decorators. The complexity was in the account linking -- making sure a user who signs up with Google and later tries another provider gets merged, not duplicated.
04

The Hard Parts

The features that kept us up late. The ones where the first three approaches did not work.

Real-time sync across views
Trading data, signal room updates, and AI chat responses all flowing through WebSockets simultaneously. Each needed different reconnection logic, different state management patterns, and careful memoization to prevent the entire UI from re-rendering when a single price ticked. We ended up with dedicated Socket.io namespaces and Zustand slices per data domain.
Gamification from scratch
No library for this. Tournaments, leaderboards, XP systems, achievement badges, and ranking tiers all had to be designed and built from zero. The leaderboard needed to update in real-time during active tournaments without hammering the database. We used Redis sorted sets for live rankings and PostgreSQL for persistence.
Real money vs. practice balances
Users pay real money through Stripe for subscriptions and marketplace access, while tournaments and practice trading run on virtual, USD-denominated balances. The two had to stay strictly separated -- real billing never touching simulated funds -- each with its own rules and transaction history, without duplicating the checkout UI.
Expo mobile parity
The mobile app needed to match the web app's core features while respecting platform conventions. Shared TypeScript types helped, but the UI diverged significantly. Lightweight Charts does not work in React Native, so we used a WebView bridge for the charting views. Push notifications, deep linking, and biometric auth added mobile-specific complexity.

Lessons Learned

01
Split Zustand stores early
We started with two large stores and quickly ran into re-render problems. When a price tick updated the trading store, unrelated components subscribed to auth state would also re-render. Splitting into domain-specific stores (auth, trading, chat, signals, ui) with Zustand's slice pattern fixed it. The rule: if two pieces of state change at different frequencies, they belong in different stores.
02
TanStack Query handles WebSocket data well
We initially managed WebSocket data purely through Zustand. Then we realized TanStack Query's cache invalidation and stale-while-revalidate patterns worked for our use case. WebSocket events would invalidate specific query keys, triggering targeted refetches instead of global state updates. This gave us automatic loading states, error boundaries, and retry logic for free.
03
Monorepo tradeoffs are real
Shared types between web and mobile saved us from drift. Shared utilities reduced duplication. But the build times, the dependency management, the Expo and Vite configs fighting each other -- it was a constant tax. For two developers, the overhead was manageable. For a solo project, I would think twice before reaching for a monorepo.
04
Gamification is deceptively complex
XP, levels, badges, tournaments, and leaderboards sound simple in a product spec. In practice, you are building a secondary economy. Edge cases multiply: What happens when a tournament ends mid-trade? How do you prevent XP farming? When do you snapshot leaderboard rankings? Each answer spawns three more questions. Budget twice the time you think you need.
05
Joining a project late is its own skill
When I joined 3 months in, the backend architecture was already set. I had to understand the existing patterns, conventions, and the reasoning behind decisions I was not part of. The fastest path was reading the existing code, not asking for documentation that did not exist. Within two weeks I had context. Within a month I was shipping faster than if I had started from scratch, because the backend foundation was solid.
